# 应用日志轮转与 180 天保留优化报表

> 生成日期：2026-07-31
> 目标：调试 / 系统运行故障信息写入 `app.log`；单文件 **> 5MB 自动生成新文件**；日志**保留 180 天**后自动清理。

## 一、需求与现状对照

| 需求 | 改造前 | 改造后 |
|------|--------|--------|
| 调试/故障信息写入 `app.log` | ✅ 已写入（`RotatingFileHandler` + `DatabaseLogHandler`） | ✅ 不变 |
| 单文件 > 5MB 生成新文件 | ⚠️ 已有 5MB 轮转，但 `backupCount=5`，只保留 5 个备份，更早的被直接覆盖删除 | ✅ 5MB 轮转保留，且由"时间保留"接管删除策略 |
| 日志保存 180 天 | ❌ 无任何时间维度保留；`backupCount=5` 最多只留 5×5MB | ✅ 每日定时清理修改时间超过 180 天的轮转备份 |
| `worker.log`（异步任务进程） | ❌ 用非轮转 `FileHandler`，无上限、无限增长 | ✅ 同步升级为 5MB 轮转，纳入 180 天清理 |

**核心问题**：原配置把"保留"误解为"保留几个文件"。在 5MB 切分下，`backupCount=5` 意味着最多 25MB 日志就被循环覆盖，既不满足 180 天，也无法应对高日志量（如监控任务大量 INFO）导致的频繁覆盖丢历史。

## 二、改动清单（3 个文件）

### 1. `utils/logging_config.py`（核心）
- 新增常量 `LOG_RETENTION_DAYS = 180`（全局保留天数，单点可调）。
- 新增函数 `cleanup_old_log_files(logs_dir=None, retention_days=LOG_RETENTION_DAYS, dry_run=False)`：
  - 仅匹配带后缀的轮转备份（文件名含 `.log.`，如 `app.log.1`、`worker.log.5`）；
  - **绝不删除当前正在写入的基础日志** `app.log` / `worker.log`（基础文件名末尾 `.log` 后无额外点，不在匹配范围，且其 mtime 持续刷新）；
  - 按"修改时间 < 现在 - 180 天"判定过期并删除；
  - 支持 `dry_run=True` 仅统计不删除，便于审计。
- `RotatingFileHandler` 的 `backupCount` 由 `5` 提升至 `1000`：大小轮转继续负责"切分新文件"，`backupCount` 退化为安全上限，真正的过期删除交给时间清理，避免与时间保留冲突。
- `setup_logging()` 末尾新增**启动时清理**：应用启动即执行一次 `cleanup_old_log_files()`，防止长期运行后堆积。

### 2. `scheduler.py`（定时清理）
- 注册每日 **03:30** 执行的 `cleanup_old_logs_job`（`CronTrigger(hour=3, minute=30)`，与 03:00 的监控数据清理错开）：
  - 函数 `cleanup_old_log_files` 不依赖 DB/应用上下文，纯文件系统操作，运行安全。

### 3. `worker.py`（worker 进程日志一致性）
- `worker.log` 的处理器由 `logging.FileHandler` 升级为 `RotatingFileHandler(maxBytes=5MB, backupCount=1000)`；
- 其轮转备份 `worker.log.N` 同样被 `cleanup_old_log_files` 的 `*.log.*` 匹配规则覆盖，自动纳入 180 天保留。

## 三、验证结果

- **语法校验**：`py_compile` 对 `logging_config.py` / `scheduler.py` / `worker.py` 全部通过。
- **功能测试**（临时目录构造，真实调用 `cleanup_old_log_files`）：
  - 构造：`app.log`(当前)、`app.log.1`(200 天前，应删)、`app.log.2`(当前，保留)、`worker.log.5`(200 天前，应删)、`notes.txt`(无关，保留)。
  - 结果：`DRY_RUN_REMOVED=2`，`REAL_REMOVED=2`，剩余 `['app.log','app.log.2','notes.txt']` ✅
  - 证明：仅删除过期轮转备份，活跃日志、新备份、无关文件均安全保留。
- **静态校验**：调度注册（`cleanup_old_logs_job` / `CronTrigger(hour=3, minute=30)` / import）、配置常量（`LOG_RETENTION_DAYS = 180` / `backupCount=1000` / `def cleanup_old_log_files`）、worker 升级均确认存在。

## 四、运行行为说明

1. **何时生成新文件**：`app.log` 达到 5MB 且要写入新日志时，自动轮转为 `app.log.1`；再次满则 `app.log.1 → app.log.2` …… 当前写入始终落在 `app.log`。
2. **何时删除旧文件**：每日 03:30 检查 `logs/` 下所有 `*.log.*` 备份，删除"最后修改时间早于 180 天前"的文件。基础 `app.log` 永远不被删（会持续被新日志刷新 mtime）。
3. **磁盘上限兜底**：即使清理任务因故未跑，`backupCount=1000` 也保证最多约 1000×5MB ≈ 5GB 的备份上限，不会无限膨胀。
4. **保留天数调整**：仅修改 `utils/logging_config.py` 中 `LOG_RETENTION_DAYS` 一处即可（如改为 90 / 365）。

## 五、边界与注意事项

- 清理依据是**文件修改时间**而非日志内容中的时间戳。轮转出去的备份文件 mtime 停在轮转那一刻，因此"180 天前轮转"= "180 天前的日志"，语义准确。
- 若服务长时间停机（>180 天）后重启，`setup_logging` 的启动清理会立即清掉所有过期备份；基础 `app.log` 因无后缀不被匹配，安全。
- 多进程场景（如 gunicorn 多 worker）下标准 `RotatingFileHandler` 在 Windows 存在极小概率的轮转竞争；当前为单进程 Flask + 单 worker 进程，无此问题。如未来扩展为多进程，建议改用 `ConcurrentLogHandler` 或集中式日志（如写入文件改为走 stdout + 外部 logrotate）。

## 六、回滚方式

- 若要回退：将 `LOG_RETENTION_DAYS` 改回行为、或删除 `scheduler.py` 中的 `cleanup_old_logs_job` 注册块，并还原 `backupCount=5`、`worker.py` 的 handler 即可。改动均为增量、非破坏性，不影响现有日志格式与 DB 日志写入。

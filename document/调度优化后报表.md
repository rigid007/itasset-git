# 调度优化后报表（1000 节点）

> 优化对象：`E:\asset` IT 资产与运维管理平台
> 优化日期：2026-07-31
> 假设规模：**1000 个被管理节点**
> 配套分析：`调度频率与1000节点负载分析.md`（优化前）

---

## 一、已实施的优化措施

| # | 文件 | 改动点 | 目的 |
|---|------|--------|------|
| 1 | `tasks/monitor.py` | `collect_device_metrics` 由单线程串行改为 `ThreadPoolExecutor(50)` 并发采集；`_save_metric` 逐条 commit 改为主线程 `bulk_insert_mappings` 一次性批量写入 | 消除头号 DB 杀手（逐条 commit）与串行堆积 |
| 2 | `utils/tasks.py` | 新增 `_collect_device_interfaces` 设备级并发采集（`POLL_WORKERS=80`）；主任务设 `POLL_TIME_BUDGET=240s` 时间预算，超时停止提交新设备；每线程独立 Redis 连接批量推送 | 接口采集从"永远跑不完"变为"预算内尽力/多轮覆盖" |
| 3 | `tasks/retention.py` | **新增模块**：`cleanup_monitoring_data` 按 `CollectionSetting.data_retention_days`（默认 30 天）分批删除过期 `MetricData` / `InterfaceMonitorData` | 防止监控时序表无限膨胀 |
| 4 | `scheduler.py` | 注册每日 03:00 的 `cleanup_monitoring_data_job`（Cron）；`collect_device_metrics` 频率 30s→60s；`run_link_monitor` 频率 120s→300s | 接入保留清理、降低高频/链路压力 |
| 5 | `tasks/link_monitor.py` | 链路检测并发 `max_workers=5→20`；`run_link_monitor` 复用 `app.link_monitor` 实例，修复每次调度新建 `ThreadPoolExecutor` 导致的线程池泄漏 | 提升链路吞吐、消除线程泄漏 |

> 校验：`py_compile` 全部通过；关键符号与调度注册静态校验 `STATIC_OK`。

## 二、优化前后任务配置对比（1000 节点估算）

| 任务 | 指标 | 优化前 | 优化后 |
|------|------|--------|--------|
| `collect_device_metrics` | 频率 | 30s | **60s** |
| | 并发 | 1（串行） | **50** |
| | 写入方式 | 每指标 1 次 commit | **bulk_insert_mappings 批量** |
| | 单轮耗时(估) | ~2400s | **~30–60s** |
| | 溢出倍数 | ~80x | **~1x** |
| `poll_all_devices_interfaces` | 并发 | 1（串行） | **80** |
| | 时间预算 | 无（跑不完） | **240s 截断** |
| | 单轮行为 | 永远堆积 | **预算内尽力 / 多轮覆盖** |
| `run_link_monitor` | 频率 | 120s | **300s** |
| | 并发 | 5 | **20** |
| | 溢出倍数(估) | ~50x | **~6x** |
| `cleanup_monitoring_data` | — | 不存在 | **每日 03:00 分批清理** |
| 调度器线程池 | link_monitor | 每次新建→泄漏 | **复用缓存实例** |
| `check_all_devices_status` | （未改） | 5 线程 / ~5.3x | 保持（见后续建议） |

## 三、数据库影响对比

| 维度 | 优化前 | 优化后 |
|------|--------|--------|
| `MetricData` 写入事务数/小时 | **~720,000 次 commit** | **~120 次 bulk 写入（降约 6000 倍）** |
| 监控数据每日新增行数 | ~24.5M 行 | ~24.5M 行（采集内容不变，行数不变） |
| 表增长趋势 | 无上限无限膨胀 | **retention 维持滚动窗口（默认 30 天）** |
| SQLite 写锁 | 必崩 | 中小规模可用；**1000 节点仍建议迁移 MySQL/PG** |
| 全表锁风险 | 清理缺失 | 分批 `LIMIT` 删除，避免长事务锁表 |

> 重要说明：**采集行数未减少**（每设备每指标仍需落库），优化核心是①消除"逐条小事务"（降 3 个数量级事务开销）、②消除任务无限堆积、③用 retention 把"无限增长"变成"滚动窗口"。后续仍需对 `MetricData` 加 `collected_at` 索引并考虑降采样。

## 四、预期效果

1. **调度不再无限堆积**：采集/链路任务能在预算或合理周期内完成，线程与 SNMP 流量趋于平稳，同进程 Web 请求不再被长期挤占。
2. **数据库事务压力骤降**：从每秒数百次微事务降到每小时百次级批量写入，SQLite 在中小规模可正常运行。
3. **库体可控**：每日清理使监控表维持在"保留天数"窗口内（默认 30 天），查询性能不再随时间线性劣化。
4. **消除线程泄漏**：链路监控复用实例，长期运行内存/线程稳定。

## 五、验证方法

1. 测试环境灌入 1000 个 mock 设备（`management_ip` 指向可控靶机或黑洞 IP 模拟离线）。
2. 启动调度，观察：
   - 各任务 `next_run_time` 与 `last_run` 差值是否回落到间隔附近（堆积消失）；
   - `MetricData` / `InterfaceMonitorData` 行数增长曲线是否在清理任务后回落；
   - 应用进程 CPU / 线程占用、Web 接口 P95 延迟；
   - 是否仍出现 `database is locked`（SQLite 下）。
3. 对照本表校准真实网络延迟后微调 `METRIC_COLLECT_WORKERS` / `POLL_WORKERS` / `POLL_TIME_BUDGET`。

## 六、残留风险与后续建议（P1/P2）

1. **`check_all_devices_status` 仍未并发优化**（仅 5 线程、~5.3x），建议提高到 20–50 线程。
2. **`evaluate_alerts` 仍对时间窗口 `.all()` 全量加载**，千万级数据下有内存尖峰，建议改为窗口聚合 / `LIMIT` + 索引过滤。
3. **`MetricData.collected_at` 缺索引**：retention 删除与告警查询会全表扫描，建议加索引（需 Alembic migration）。
4. **接口采集设备内仍串行**：可进一步改为接口级并发，缩短单设备采集时间。
5. **`task_scheduler.py` 的 `DeviceMonitorScheduler` 当前未启用（死代码）**：建议移除或在文档明确禁用，避免误启用造成双倍 ping/SNMP 轮询。
6. **降采样**：原始指标建议额外落"按小时聚合表"，长期趋势查询不再扫描原始明细。

## 七、回滚说明

每项改动相互独立，可针对单文件回退：
- `tasks/monitor.py`、`utils/tasks.py`、`tasks/retention.py`、`scheduler.py`、`tasks/link_monitor.py` 均为增量修改；
- 若清理任务需临时关闭，删除 `scheduler.py` 中 `cleanup_monitoring_data_job` 注册段即可，不影响采集逻辑；
- 并发参数（`METRIC_COLLECT_WORKERS`、`POLL_WORKERS`、`POLL_TIME_BUDGET`）均为模块级常量，便于按硬件微调。

*注：所有耗时与倍数为基于代码逻辑的估算，实际数值取决于网络延迟、设备响应与并发参数；结构性改善（批量提交、并发、保留清理）与规模无关，必然生效。*

 一、关键 Bug（功能无法正常使用）
  1. blueprints/monitor.py 使用了错误的蓝图变量名
  blueprints/monitor.py:16 — 在 monitor_bp 蓝图下使用了 @monitoring_bp.route，这个变量名不存在，会导致 NameError。

  2. utils/utils.py 变量引用自身的 bug

  get_device_snmp_data() 函数（第1213-1214行）：
  community = community or getattr(device, 'snmp_community', 'public')
  version = str(version or getattr(device, 'snmp_version', '2c'))
  community 和 version 引用了自身的变量（尚未定义）。这里应该使用默认值硬编码或无参使用已存在的局部变量。

  3. get_device_snmp_data() 中的 vendor 判断逻辑错误

  第1220行 dt = device.device_type.lower() 判断的是 device_type（如 'switch'、'router'），却用这个来判断厂商（如
  'cisco'、'h3c'）。逻辑混乱。

  4. 重复的 API 路由导致第二个无效

  app.py 中有两个 @app.route('/api/activities')：
  - 第758行：带分页筛选的完整实现
  - 第806行：简单的 limit(200) 版本

  Flask 中重复路由会导致第一个被第二个覆盖。

  5. Device.is_deleted 字段不存在但被使用

  blueprints/monitor.py:30 和 blueprints/monitor.py:87 使用了 Device.query.filter_by(is_deleted=False)，但 Device
  模型中不存在此字段。

  6. Device.firmware_version、Device.network_usage、Device.uptime 等字段不存在

  blueprints/monitor.py 第130-135行引用了
  device.firmware_version、device.network_usage、device.uptime，但模型中无此字段。

  7. 通知功能完全不可用

  blueprints/monitoring.py 中 send_test_notification() 调用了 send_email(), send_sms(), send_webhook()
  等函数，但全部未导入也未实现。

  8. routes.py 中重复的变量赋值

  第113-120行 recent_activities 被重复定义了两次，第二次覆盖了第一次。

  9. check_topology_periodically 线程引用不存在的模型属性

  app.py:710 访问了 rel.remote_device_name 和 rel.remote_interface，但 InterfaceRelationship
  模型（models/models.py:323）中这两个属性并不存在（只有 local_interface 和 remote_interface，但实际列定义缺少
  remote_device_name）。

  四、设计/架构问题

  16. 模型定义分散且大量重复

  共 14 个模型文件，大量重叠：
  - models/models.py — 核心模型（~2017行，包含所有关系定义）
  - models/monitoring.py — 单独定义了 DeviceConfig、MetricData、AlertHistory、Rule
  - models/settings_models.py — 只包含 SystemConfig（与 Config 模型高度重复）
  - models/device_performance_models.py — DevicePerformance（与 PerformanceMetric 及 MonitorData 大量重叠）

  17. Device.monitor_configs 和 DeviceConfig 关系冲突

  - models/models.py:1955: Device.monitor_configs = db.relationship('DeviceMonitorConfig', ...)
  - models/monitoring.py:80: Device.monitor_config = db.relationship('Device', backref=db.backref('monitor_config',
  ...))
  两个不同的 relationships 指向不同的表名但属性名冲突，可能导致映射错误。

  18. 配置加载顺序混乱

  app.py:36 先通过 app.config.from_object('config.Config') 加载配置，但紧接着第42-46行又用硬编码覆盖。app.py 中的
  CSRFProtect 初始化在第39行，早于一些配置设置。

  19. 数据库初始化逻辑重复

  - exensions.py 中的 init_extensions() 也调用了 db.create_all()
  - app.py 中的 init_database() 也调用了 db.create_all()
  谁先调用不确定，可能造成初始化顺序问题。

  20. 两个独立的调度器实例

  - extensions.py（第53行起的注释块）已经定义了一个调度器
  - scheduler.py（实际上又是另一个 extensions.py 的副本）又创建了第二个
  - app.py:863 调用 configure_scheduler(app) 时又有第三个

  21. ping_device 函数签名不一致引起隐患

  - utils/utils.py:73: 返回 (bool, float) 元组
  - utils/tasks.py:673: 返回 bool
  使用 utils/tasks.py 版本的地方如果期望解包元组，会得到 TypeError。

  22. 活动日志记录逻辑有误

  app.py:821 的 log_activity() 函数在内部再次 import current_user，这种做法容易出问题，且与顶部已导入的 current_user
  矛盾。

  五、性能问题

  23. routes.py 仪表盘 N+1 查询

  每一次加载仪表盘，都会为每个机柜单独查询设备数量：
  for cabinet in cabinets:
      used_slots = Device.query.filter_by(cabinet_id=cabinet.id).count()
  每多一个机柜就多一个 SQL 查询。应该用 GROUP BY 一次查出。

  24. monitor_connections() 逐条提交

  utils/tasks.py:1284-1290 每处理 10 条连接就 commit 一次，而不是批量一次提交。

  25. SNMP 采集串行处理

  utils/tasks.py:98 中 poll_all_devices_interfaces() 通过 for 循环串行采集所有设备，没有利用
  ThreadPoolExecutor，在大规模网络下耗时较长。

  26. 数据库日志模式下每次都 commit()

  app.py:227 的 DatabaseLogHandler.emit() 每条日志都会 commit()，高频日志场景下性能极差。应采用批量写入。

  六、需要改进的方面

  27. 模板过滤器重复定义

  - app.py:348-356: get_status_color 在模板过滤器中定义
  - app.py:391-399: 同样的 get_status_color 在上下文处理器中又定义一遍

  28. SystemLog 两个模型表名冲突

  models/config_models.py 和 app.py 中的 DatabaseLogHandler 都引用 SystemLog 模型，但实际上 models/settings_models.py
  只有一个 SystemConfig 模型。SystemLog 模型可能根本没有正确定义。

  29. scheduler.py 文件内容实际上是 extensions.py

  文件名为 scheduler.py，但内容全是 extensions.py 的代码。这是一个严重命名错误——真正的 scheduler.py
  应该只负责调度配置，而不是整个扩展初始化。

  30. 缺少健康检查机制

  虽然有 /api/health 端点，但整个系统缺少对后台线程（拓扑检测、SNMP 采集、Redis
  消费者）是否存活的可视化监控和自动恢复机制。
